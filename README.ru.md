## Позиционирование проекта

Этот репозиторий описывает не универсальный десктопный AI-инструмент для разработки, а внутреннюю веб-платформу AI R&D, адаптированную на основе OpenCode.

- Это **Web-first** внутренний продукт; текущий фокус адаптации — веб-приложение
- Он предназначен для **многопользовательской совместной работы** в организации, а не для локального использования одним разработчиком
- Он не позволяет свободно подключаться к каталогам сервера; пользователи работают в рамках **границ проектов, контролируемых администратором**
- Он предоставляет **единые возможности AI-платформы**, а не только страницу «чат с AI для редактирования кода»

Его можно понимать как:

> Контролируемый, управляемый AI R&D workbench для внутреннего использования несколькими пользователями.

## Наша философия

Платформа стремится стать единой внутренней платформой AI R&D, а не просто страницей AI-разработки.

Ключевые принципы:

- **Не удалённый рабочий стол, а AI workbench в рамках контролируемых проектов**
- **Не для того, чтобы немногие разработчики монополизировали AI, а чтобы больше ролей участвовали в производстве ПО в рамках своих полномочий**
- **Не AI, которое только отвечает на вопросы, а AI, постепенно становящееся исполнительным слоем в R&D-процессе**
- **Не снятие границ, а повышение эффективности при управлении правами, проектами, сессиями и моделями**

В плане продукта три ключевые границы:

- **Граница проекта**: обычные пользователи могут получить доступ только к проектам, зарегистрированным администраторами
- **Граница сессии**: одна задача соответствует одной независимой сессии и одному рабочему пространству
- **Граница прав**: что видят пользователи, что могут делать и какие модели использовать — контролирует платформа

## Текущие ключевые возможности

Адаптация сосредоточена на веб-приложении:

- Многопользовательская регистрация, вход и управление учётными записями
- Возможности пользователей, проектов, моделей и аудита, видимые администраторам
- Регистрация проектов для раскрытия только одобренных репозиториев кода
- Изолированные рабочие пространства по сессиям, как правило через Git worktrees
- Единое управление моделями, провайдерами, правами и режимами
- Единая точка входа в AI-платформу для команд

Фокус не на десктопе и TUI, а на:

> Возможности пользователям внутри организации выполнять Q&A, анализ, редактирование, выполнение и совместную работу через веб в рамках контролируемых проектов.

## Многопользовательский режим и единая AI-платформа

Платформа не даёт полный доступ всем, кто вошёл. Вместо этого:

1. Администраторы подготавливают код проекта на сервере
2. Администраторы регистрируют разрешённые каталоги как проекты
3. Пользователи регистрируются и входят через веб
4. Обычные пользователи видят только проекты, открытые для них
5. Пользователи начинают работу в сессиях после входа в проект

Единая AI-платформа обеспечивает:

- Единую точку входа моделей
- Единое управление провайдерами
- Единый контроль прав
- Единый рабочий процесс по сессиям
- Единые границы аудита и управления

Такая архитектура поддерживает постепенное внутреннее внедрение: сначала с правами низкого риска, затем расширение по ролям и сценариям.

## Поддержка Cursor CLI

Платформа поддерживает **Cursor CLI** как источник моделей/провайдера в единой AI-платформе.

### Как подключить

На сервере должен быть установлен Cursor CLI, а команда `agent` в shell должна быть доступна:

```bash
agent login
```

После входа платформа повторно использует существующее локальное состояние входа Cursor.

### Использование в платформе

- Администраторы управляют тем, могут ли пользователи получать доступ к моделям и провайдерам
- Ограниченные по умолчанию пользователи обычно имеют только режим `ask`
- Белый список моделей по умолчанию обычно включает:
  - `cursor-cli/auto`
  - `cursor-cli/composer-1`
  - `cursor-cli/composer-1.5`

Если Cursor CLI не установлен или `agent` недоступен, модели и провайдеры Cursor CLI не появятся в платформе.

### Рекомендации по настройке

Для первоначального внутреннего внедрения:

- Ограниченные по умолчанию пользователи: только режим `ask`
- Белый список моделей по умолчанию: предпочитать модели `cursor-cli`
- Не экспонировать Provider, Server, MCP и другое управление высокого риска по умолчанию
- Позволять администраторам расширять возможности по пользователям или ролям по мере необходимости

Преимущества:

- Низкая стоимость внедрения
- Чёткие границы риска
- Единый источник моделей
- Простая UX для внутреннего внедрения

### Роль в системе

При подключённом Cursor CLI платформа не просто вызывает внешний API модели. Она собирает контекст сессии, границы проекта и инструменты платформы и передаёт их в Cursor CLI для выполнения.

Таким образом, `cursor-cli` здесь — не изолированный инструмент, а часть единой AI-платформы.

## Рекомендации по внедрению для администраторов

Рекомендуемый подход:

1. Подготовить контролируемые каталоги проектов
2. Регистрировать только явно одобренные репозитории
3. Давать обычным пользователям ограниченные права по умолчанию
4. Приоритизировать веб Q&A и возможности низкого риска
5. Постепенно добавлять больше моделей, режимов и функций рабочего процесса

Кратко: не включать всё сразу. Вместо этого:

> Сначала установить границы проектов, прав, моделей и сессий, затем расширять возможности платформы шаг за шагом.

## Локальная разработка

Фокус адаптации — веб-приложение, поэтому локальная разработка должна запускать веб-стек.

Установка зависимостей:

```bash
bun install
```

Запуск одной командой:

```bash
sh restart-services.sh
```

Адреса по умолчанию:

- Сервер: `http://localhost:4096`
- Frontend: `http://localhost:3000`

Для раздельного запуска:

```bash
bun run --cwd packages/opencode dev
bun run --cwd packages/app dev
```
