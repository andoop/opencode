# 公司内部 AI 研发平台一页版判断

## 1. 一句话结论

这个平台值得继续做，但前提是：

> 我们做的是“受治理的内部 AI 研发执行平台”，而不是“内部版 AI 聊天工具”。

平台的必要性不在模型本身，而在于：

- 组织级治理
- 多角色协作
- 研发流程闭环
- 统一审计与责任追踪

---

## 2. 为什么值得做

如果公司真正需要下面这些能力，平台就有明确价值：

- 统一模型入口和成本控制
- 项目白名单和访问边界
- 权限、模式、工具、分支的治理
- 非开发角色在受控范围内发起代码工作
- 从需求、Bug 到修复、测试、PR、回归的任务闭环

这些问题不是单个 AI coding 工具能完整解决的，更适合由平台承接。

---

## 3. 什么情况下不值得做

如果平台最终只是：

- 一个 Web 聊天页
- 一些模型配置能力
- 一些简单代码操作能力

但没有治理、闭环和组织级流程价值，那么必要性很弱。

如果团队通过现成工具组合已经能解决大部分问题，例如：

- Cursor
- Continue
- OpenHands
- Git 平台
- 工单系统
- CI/CD

那么平台必须证明自己解决了这些组合方式解决不了的问题，否则就属于重复造轮子。

---

## 4. 我们真正该解决的问题

平台最该解决的不是“AI 会不会写代码”，而是：

- 如何把 AI 纳入公司内部研发治理体系
- 如何让产品、开发、QA 在同一平台中协作
- 如何让任务在系统中流转，而不是在人之间反复沟通
- 如何沉淀组织级能力，而不是依赖少数高手

也就是说，平台的核心不是聊天，而是：

- 项目边界
- 权限边界
- 会话与任务隔离
- 执行与审计
- 结果解释与责任闭环

---

## 5. 最值得聚焦的三个场景

### 5.1 PRD / 需求说明 -> AI 生成可验证版本

目标：

- 产品输入 PRD、页面说明、原型
- AI 在独立工作区生成可运行版本
- 自动构建和预览
- 产品快速判断方向是否成立

价值：

- 缩短“想法 -> 可验证结果”的时间
- 降低需求验证成本

### 5.2 Bug / 工单 -> AI 修复 + PR / MR

目标：

- QA 提交 bug
- 平台补齐上下文
- AI 修复并执行相关测试
- 自动生成 PR / MR
- 开发 review
- QA 回归确认

价值：

- 缩短 bug 修复链路
- 减少 QA 和开发之间的重复沟通

### 5.3 代码变更 -> AI Review + 测试补齐 + 回归建议

目标：

- 自动 review 代码变更
- 自动识别风险和影响面
- 自动建议补充测试
- 自动生成回归建议

价值：

- 把质量前移
- 让 AI 不只会改代码，也会解释风险

---

## 6. 下一阶段只建议先打穿一个场景

如果只能选一个，建议优先做：

> `Bug -> AI 修复 -> PR / MR -> QA 回归`

原因：

- 边界比需求实现更清晰
- 输入更结构化
- 更容易接入现有 Git / CI / 测试体系
- 更容易量化收益
- 更容易让 QA、开发、管理层都感知到价值

这条链路跑通后，平台就不再只是“会话系统”，而开始像“研发执行系统”。

---

## 7. 第一阶段不要做什么

为了避免发散，先不要同时做：

- 大而全的外部系统集成
- 超复杂组织权限模型
- 全量任务编排平台
- 大量角色门户
- 大报表系统
- 一次性打通所有链路

先证明一个高价值闭环，再扩能力。

---

## 8. 怎么判断平台值不值得继续投

后续不应只看愿景，而应看结果。

重点观察以下指标：

- bug 从提单到 PR 的平均时间
- bug 从提单到回归完成的平均时间
- AI 生成可 review 修复的比例
- QA / 开发来回沟通轮次
- 合并后的返工率和回归率

如果 1 到 2 个季度后，核心闭环没有明显改善，就应该收缩而不是继续铺大。

---

## 9. 对当前平台的阶段性判断

- 方向是成立的
- 必要性是有条件成立的
- 最大价值不在 AI 本身，而在治理和闭环
- 下一阶段最重要的不是加功能，而是证明一个真实场景能显著优于现有协作方式

一句话总结：

> 平台不是靠功能堆出来的，而是靠一两条闭环把价值打穿之后，反过来成立的。

---

## 10. 建议的推进顺序

1. 先证明 `Bug -> AI 修复 -> PR / MR -> QA 回归`
2. 再扩展到 `PRD -> AI 实现 -> 预览验证`
3. 最后补齐质量闭环、组织治理和外部系统联动
