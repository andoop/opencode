# 公司内部 AI 编码 Web 端使用手册

## 1. 文档目的

本文档用于说明公司内部 AI 编码 Web 端的使用方式，帮助管理员和普通用户理解以下内容：

- 系统整体是怎么运行的
- 项目机制是什么
- 会话是干什么的
- 日常应该怎么使用
- 常见问题如何理解

这套系统的目标不是让用户随意访问服务器电脑上的任意目录，而是在管理员预先控制的项目范围内，让大家安全地进行问答、代码分析、代码修改和命令执行。

---

## 2. 系统整体机制

系统运行方式可以简单理解为：

1. 管理员在一台受控电脑上运行服务。
2. 管理员提前在这台电脑上准备好公司项目代码，并将允许使用的目录注册为“项目”。
3. 公司成员通过 Web 页面访问服务。
4. 用户通过手机号注册并登录。
5. 普通用户只能进入管理员已经开放的项目，不能任意打开电脑上的其他目录。
6. 用户在选定项目后，通过“会话”开展问答、改代码、查看变更、使用命令行等操作。

因此，这套系统的核心不是“远程桌面”，而是“受控项目内的 AI 工作台”。

---

## 3. 角色说明

### 3.1 管理员

管理员负责控制系统边界，主要职责包括：

- 注册可使用的本地项目目录
- 管理用户
- 配置用户权限
- 控制哪些模式、模型、管理入口对哪些用户可见

管理员决定“用户能进哪些项目、能看到哪些功能、能做多大范围的操作”。

### 3.2 普通用户

普通用户登录后：

- 只能看到管理员已经注册的项目
- 只能使用被授权的模式和模型
- 看不到未开放的管理入口
- 不能自行浏览服务器电脑上的任意目录

当前默认注册用户的受限策略通常为：

- 仅开放 `ask` 模式
- 不开放模型、供应商、服务器等管理能力
- 可用模型仅限：
  - `cursor-cli/auto`
  - `cursor-cli/composer-2.5`
  - `cursor-cli/composer-2.5-fast`

这种默认策略适合先在公司内部低风险推广。

## 4. 项目机制

## 4.1 什么是项目

项目就是管理员预先登记的一份本地代码目录，通常对应一个真实仓库。

例如：

- 前端仓库
- 后端仓库
- 移动端仓库
- 工具链仓库

这些代码仓库先由管理员放在服务运行的电脑上，再注册进系统。之后普通用户只能从这些已登记项目中进行选择。

## 4.2 项目机制解决了什么问题

项目机制主要解决以下问题：

- 限制操作范围：普通用户不能随意访问服务器上的其他目录
- 统一运行环境：所有人都基于同一台机器上的统一代码和依赖环境工作
- 便于治理：项目由管理员统一维护、统一开放

可以把“项目”理解为：

“公司允许你进入的一份代码仓库入口”。

## 4.3 推荐做法

管理员应当只注册公司明确允许使用的项目目录，例如：

- 主业务仓库
- 公共组件库
- 内部工具仓库

不建议注册无关目录、个人目录或临时目录。

## 5. 会话机制

## 5.1 什么是会话

会话不是单纯的一段聊天记录，而是一份与当前任务绑定的独立工作上下文。

一个会话通常会包含：

- 本次任务的对话历史
- 本次任务的工作目录
- AI 在该任务中的文件操作和命令执行记录
- 该任务对应的变更信息

可以把会话理解为：

“这次任务专属的小工作台”。

## 5.2 为什么要有会话

如果所有用户都直接在同一个项目目录上连续工作，会出现很多问题：

- 多个任务混在一起，历史很难回看
- 不同用户之间容易互相影响
- 同一个用户做多个任务时容易串上下文
- 很难判断某次任务到底改了什么

因此系统将工作过程拆分成一个个会话。

## 5.3 会话实际做了什么

创建新会话后，系统通常会围绕该项目准备一个独立工作空间，并把后续操作都绑定到这次会话。

这通常包括：

- 为该会话准备独立工作目录
- 将对话、文件操作、命令执行与该会话关联
- 记录会话期间产生的代码变更

在当前系统设计中，会话通常尽量对应一个独立的 Git worktree 工作区。这样做的价值是：

- 一个任务对应一个工作区，边界清晰
- 不同会话之间互相隔离，降低冲突
- 更容易回顾某个任务产生了哪些修改

## 5.4 为什么推荐一任务一会话

建议公司内部统一采用以下习惯：

- 修一个 bug，开一个会话
- 做一个需求，开一个会话
- 分析一个问题，开一个会话
- 只做问答，也可以开一个会话

这样做的好处是：

- 任务边界清晰
- 变更范围清晰
- 历史记录清晰
- 后续回看和排查更方便

不建议把多个完全无关的问题长期堆在同一个会话里。

## 6. 模式说明

## 6.1 Ask 模式

`ask` 模式适合：

- 询问代码逻辑
- 理解模块结构
- 让 AI 解释报错原因
- 让 AI 给出修改建议或实施方案
- 低风险地进行代码阅读和问题分析

对产品、设计、QA、项目经理等不以直接改代码为主的角色尤其合适。

## 6.2 为什么默认只开放 Ask

默认只开放 `ask` 模式有以下好处：

- 风险低
- 容易推广
- 不会一开始就把写文件、改配置、执行高风险操作全部放开
- 更适合作为公司内部初期的标准能力

如果后续业务需要，管理员可以按人或按角色逐步开放更多能力。

## 7. 命令行机制

会话内打开的命令行不是全局终端，而是跟随当前会话工作区的终端。

也就是说：

- 你在某个会话里打开命令行
- 命令默认就在该会话对应的工作目录中执行

这样做的目的是：

- 让命令执行和当前任务保持一致
- 避免误在错误目录下执行命令
- 保持“一个会话一个工作台”的一致性

---

## 8. 变更视图怎么理解

## 8.1 Git 变更

Git 变更更接近“当前工作区此刻的 Git 状态”。

它通常用于查看：

- 当前有哪些文件已修改
- 哪些文件新增、删除、重命名
- 当前差异内容是什么

## 8.2 会话变更

会话变更更偏向“这次会话过程中发生过或累计过的变化”。

它不一定完全等同于“你此刻手动看到的当前 Git 状态”。

所以有时会出现这种情况：

- 用户感觉自己没有继续手动修改
- 但会话变更里仍然显示很多变化

常见原因包括：

- AI 在本次会话里改过代码
- 会话中执行过格式化、生成文件、安装依赖等操作
- 中间步骤产生过临时或批量改动
- 会话变更记录的是会话过程中的累计变化，而不是只看当前这一下

简单理解：

- Git 变更：更像当前实时状态
- 会话变更：更像本次任务过程记录

## 9. 普通用户使用流程

## 9.1 注册与登录

1. 打开系统登录页。
2. 使用中国大陆手机号注册。
3. 输入密码并再次确认密码。
4. 注册成功后登录系统。

说明：

- 手机号是唯一账号 ID
- 默认权限由管理员或系统策略控制

## 9.2 选择项目

1. 登录后进入首页。
2. 从管理员已开放的项目中选择一个项目。
3. 进入项目后，建议立即创建新会话。

## 9.3 创建会话

1. 点击“新建会话”。
2. 等待系统为本次任务准备工作区。
3. 创建完成后进入会话页面。

创建会话可能涉及 Git worktree 等操作，因此需要一定时间。等待期间请不要重复点击。

## 9.4 在会话中工作

在会话中可以进行以下操作：

- 提问和追问
- 查看代码
- 分析问题
- 查看变更
- 打开命令行

如果当前账号只开放了 `ask` 模式，那么这属于权限设计，不是异常。

## 9.5 完成任务

任务完成后建议：

- 回看本次会话记录
- 确认会话变更或 Git 变更
- 不再需要时关闭或删除该会话

然后为下一个任务重新创建新会话。

## 10. 管理员使用流程

## 10.1 准备项目

管理员应先在服务器电脑上准备好项目代码，例如提前 clone 业务仓库，并确保依赖和基础环境可用。

## 10.2 注册项目

管理员将允许开放的本地目录添加为系统项目。项目添加完成后，普通用户才能看到并使用。

## 10.3 管理用户

管理员可以：

- 查看用户
- 创建用户
- 编辑用户
- 调整用户权限
- 限制用户可见功能和可用模型

## 10.4 推荐权限策略

建议先采用分层开放策略：

- 默认注册用户：仅开放 `ask`
- 开发同学：按需开放更多模式和模型
- 管理员：保留完整能力

这样更适合公司内部逐步推广，先控风险，再扩能力。

## 11. 常见问题 FAQ

### 11.1 为什么我看不到某些项目？

因为普通用户只能看到管理员已注册并允许访问的项目。看不到通常不是系统异常，而是权限范围内没有开放。

### 11.2 为什么我登录后只能看到 Ask 模式？

这是当前账号权限配置的结果，表示该账号只允许进行问答和分析，不开放更高风险能力。

### 11.3 为什么我看不到模型、服务器、供应商等入口？

这些入口属于权限控制项。如果账号未被授予对应权限，前端会隐藏入口，后端也会拒绝相关请求。

### 11.4 为什么进入项目后没有会话？

说明当前项目下还没有可用会话。此时应先新建会话，再开始工作。

### 11.5 为什么创建会话会比较慢？

因为系统可能需要执行 Git worktree、目录准备、上下文初始化等操作，这些操作本身需要时间。

### 11.6 为什么会话变更里有很多内容，但我感觉自己没改这么多？

因为会话变更不一定只代表你“此刻手动修改了哪些内容”，也可能包含本次会话过程中 AI 操作、格式化、生成文件等累计影响。

### 11.7 为什么建议一个任务一个会话？

因为这样最容易做到：

- 任务隔离
- 变更隔离
- 历史可追踪
- 回滚和排查更方便

---

## 12. 建议的内部使用规范

建议公司内部统一采用以下规范：

1. 一个任务对应一个会话。
2. 优先在受限权限下使用，按需升级能力。
3. 非管理员不要尝试绕过项目边界。
4. 会话完成后及时整理结果。
5. 遇到异常时优先查看当前项目、当前会话和当前权限是否正确。

---

## 13. 一句话总结

这套系统里：

- 项目是“管理员预先开放的代码仓库入口”
- 会话是“某次任务专属的独立工作台”
- 权限决定“你能看到什么、能做什么”

推荐的使用习惯是：

“先选项目，再开会话，一个任务一个会话，在授权范围内使用 AI 完成问答、分析和代码工作。”
