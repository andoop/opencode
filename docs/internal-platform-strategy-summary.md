# 公司内部 AI 研发平台阶段性判断总结

## 1. 文档目的

本文档用于整理当前关于公司内部 AI 研发平台的阶段性判断，帮助团队快速回顾以下几个核心问题：

- 这个平台是否有必要继续做
- 它和现有开源项目的关系是什么
- 未来最值得聚焦的高价值场景是什么
- 下一阶段应该如何用最小投入证明平台价值

这不是一份详细需求文档，而是一份面向团队对齐的战略摘要。

---

## 2. 核心结论

当前平台是有必要性的，但前提很明确：

- 必要性不在于“再做一个 AI 聊天或写码工具”
- 必要性在于“把 AI 变成组织内部研发流程的执行层”
- 平台真正的价值来自治理、协作闭环和组织级能力沉淀，而不是模型调用本身

换句话说：

> 如果我们只是想提供一个内部版 AI 对话入口，必要性很弱。
> 如果我们想建设一个受治理的内部 AI 研发执行平台，这件事是有价值的。

---

## 3. 为什么平台有必要

结合当前产品定位，平台的价值主要来自以下几个方面：

### 3.1 把 AI 从个人工具变成组织能力

市面上的 AI coding 工具大多服务个人开发者提效，但公司内部真正需要的往往是：

- 统一模型入口
- 统一权限控制
- 项目白名单和访问边界
- 审计记录和责任追踪
- 非开发角色在受控范围内参与软件生产

这些能力天然更适合做成平台，而不是依赖个人本地工具组合。

### 3.2 把研发协作从“人找人”变成“任务流转”

当前很多协作依赖人工沟通：

- 产品提需求后找开发对齐
- QA 提 bug 后等开发排查
- 测试 case、代码实现、回归验证之间长期断裂

平台的意义在于把这些动作平台化，让任务在系统中流转，而不是在人之间反复转述。

### 3.3 让更多角色真正参与软件生产

未来不是只有开发可以驱动代码变化。

在权限可控、项目可控、结果可审核的前提下：

- 产品可以用 PRD 驱动 AI 生成可验证版本
- QA 可以用 bug 单驱动 AI 进入修复闭环
- 实施、运营、设计等角色也可以在低风险场景中发起工作

平台降低的是执行门槛，但不能降低治理要求。

---

## 4. 平台没有必要的情况

也需要客观看到，平台不是天然成立的。以下情况会显著削弱必要性：

### 4.1 如果目标只是做一个内部版聊天工具

如果平台最终只是：

- 一个 Web 聊天页面
- 一些模型配置能力
- 一些简单代码操作能力

但没有任务闭环、治理能力和外部系统联动，那么必要性不强。

### 4.2 如果组合现有工具已经能解决大部分问题

如果团队用现成工具组合就能解决 70% 以上问题，例如：

- Cursor
- Continue
- OpenHands
- 工单系统
- Git 平台
- CI/CD

那么自建平台必须回答清楚：它到底解决了什么是这些工具组合解决不了的。

### 4.3 如果平台没有形成明确的高频价值场景

平台类项目最容易失败的方式，不是方向错误，而是功能很多、场景不深。

如果平台迟迟无法在一个真实闭环中证明自己显著更快、更稳、更可控，那么必要性会越来越弱。

---

## 5. 和现有开源项目的关系

全网和 GitHub 上确实已经有不少接近我们目标的开源项目，但它们大多只覆盖目标的一部分。

### 5.1 接近“AI 开发执行器”的项目

- `OpenHands`
- `SWE-agent`
- `Ralph Platform`
- `Tekton`
- `Plandex`
- `Aider`

这类项目更强在：

- 读代码
- 改代码
- 跑命令
- 从 issue 到 PR
- 后台执行 agent 任务

但它们通常不完整覆盖企业内部平台需要的多用户治理、权限模型和组织级协作。

### 5.2 接近“企业内部 AI 平台”的项目

- `LibreChat`
- `Open WebUI`
- `Onyx`

这类项目更强在：

- 多用户
- RBAC 或组织权限
- SSO / 企业集成
- 自托管
- 管理后台

但它们通常不是围绕研发执行闭环设计的，和代码工作流的耦合没有那么深。

### 5.3 接近“QA / Review 自动化”的项目

- `PR-Agent`

这类项目更适合补 AI review、PR 评论、变更分析等能力，但本身不是完整的平台。

### 5.4 结论

目前没有看到一个开源项目可以直接完整替代我们想做的事情。

更现实的策略不是“找一个整体替代品”，而是：

- 保留自己的平台主干
- 尽量少自研通用层
- 借鉴或集成开源项目在某一层已经做成熟的能力

也就是说：

> 我们不必重复造所有轮子，但我们仍然可能需要自己的平台层。

---

## 6. 平台真正该解决的问题

平台的独特价值不应放在“模型能力”上，而应放在以下几类问题上：

- 如何把 AI 纳入公司内部研发治理体系
- 如何让不同角色在同一平台中协作
- 如何让需求、Bug、测试、代码、PR、回归形成闭环
- 如何沉淀组织级能力，而不是依赖少数高手的熟练度

真正值得自研和沉淀的，不是一个聊天框，而是：

- 项目边界
- 会话与任务隔离
- 权限与审计
- 任务流转
- 结果解释和责任闭环

---

## 7. 最值得聚焦的三个高价值场景

如果平台要继续推进，不建议先做“大而全”，而应该先打穿少数几个高价值场景。

当前最值得聚焦的三个场景是：

### 7.1 场景一：PRD / 需求说明 -> AI 生成可验证版本

目标不是让 AI 一次性完成所有功能，而是：

- 产品提交 PRD、页面说明、交互草图
- AI 在独立工作区中生成一个可运行版本
- 自动构建和预览
- 产品快速验证方向是否正确

这个场景的价值在于缩短“想法 -> 可验证结果”的时间。

### 7.2 场景二：Bug / 工单 -> AI 修复 + PR / MR

这是最值得优先打穿的闭环。

理想流程是：

1. QA 或测试提交 bug
2. 平台自动补全上下文
3. AI 在独立 workspace 中分析和修复
4. 自动执行相关测试
5. 自动生成 PR / MR
6. 开发 review
7. QA 回归确认

这个场景最容易证明平台价值，因为输入更结构化、边界更清晰、指标也更容易量化。

### 7.3 场景三：代码变更 -> AI Review + 测试补齐 + 回归建议

该场景强调质量前移，目标包括：

- 自动 review 代码变更
- 自动分析风险和影响面
- 自动建议补哪些测试
- 自动生成 case 或回归建议

这条链路是平台走向“可放心使用”的关键，而不只是“会修改代码”。

---

## 8. 三个场景里最应该优先打穿哪一个

如果只能选一个先做，建议优先做：

> `Bug -> AI 修复 -> PR / MR -> QA 回归`

原因如下：

- bug 修复比需求实现更容易定义边界
- 输入更结构化，通常有标题、描述、日志、截图、复现步骤
- 更容易接入现有 Git / CI / 测试体系
- 更容易量化价值
- 更容易让 QA、开发、管理层都感知到收益

这条链路一旦打通，说明平台已经具备：

- 理解任务
- 组织上下文
- 执行代码修改
- 自动验证
- 进入 review 流程
- 回到 QA 验证

这基本就是平台最核心价值的缩影。

---

## 9. 下一阶段不该优先做的事情

为了避免平台继续发散，下一阶段不建议一开始同时做以下内容：

- 完整 ONES 深度集成
- 超复杂组织权限模型
- 大而全的任务编排系统
- 多角色超复杂门户
- 完整报表和运营分析系统
- 一次性打通需求、Bug、测试、发布所有链路

这些方向都重要，但在平台尚未证明单个闭环价值之前，不应优先投入。

---

## 10. 最小可证明价值路线

下一阶段最合理的战略，不是把平台做得更全，而是：

> 用最小投入，在一个真实研发闭环里证明 AI 可以成为第一执行层。

建议的最小闭环如下：

### 10.1 输入

QA / 测试 / 实施提交 bug，输入包括：

- 标题
- 描述
- 复现步骤
- 目标项目
- 目标分支
- 可选截图、日志、报错信息

### 10.2 平台自动组织上下文

平台补全执行所需上下文，例如：

- 最近相关提交
- 涉及文件
- 最近失败测试
- 项目权限和执行模式
- 可用模型和工具

### 10.3 AI 在独立工作区执行

AI 在独立 session / workspace 中完成：

- 问题理解
- 根因分析
- 代码修改
- 测试执行

### 10.4 自动输出结果

平台输出：

- 修复说明
- 根因分析
- 代码变更
- 测试结果
- 风险提示
- PR / MR

### 10.5 人工兜底

- 开发负责 review、判断修复方向是否正确
- QA 负责回归确认和关闭缺陷

未来分工不是消失，而是从“按职业交接”转成“按责任分工”。

---

## 11. 第一阶段应该限制在哪些 bug 上

为了控制复杂度，第一阶段建议只支持以下几类 bug：

- 前端页面逻辑 bug
- 接口参数或状态处理 bug
- 明确报错的后端逻辑 bug
- 有稳定复现路径的缺陷
- 有明确测试入口的缺陷

先不要把高风险问题纳入自动修复首批范围，例如：

- 数据迁移类
- 存储一致性类
- 权限安全类
- 并发竞态类
- 高风险基础设施类

---

## 12. 平台当前最值得补强的能力

如果从当前仓库状态出发，接下来更值得补强的不是“AI 会不会改代码”，而是以下几个方向：

### 12.1 质量与交付底座

- 统一测试入口
- 补齐 CI 测试矩阵
- 明确 lint / typecheck / test 边界
- 增加部署级可观测性
- 做依赖和供应链治理

### 12.2 平台扩展性

- 优化审计和摘要查询性能
- 重构存储抽象，为未来多实例和更高规模预留空间
- 清理服务端模块耦合

### 12.3 企业落地能力

- 企业身份体系
- 组织化权限模型
- 更稳妥的默认安全策略

### 12.4 任务流层

平台当前更偏 `session` 中心，后续如果要真正承接流程闭环，需要逐步引入：

- bug 任务
- 修复任务
- review 状态
- 回归状态
- 任务归档与审计

也就是说，后续应该让 `session` 更像任务执行容器，而不是唯一业务主对象。

---

## 13. 如何判断平台值不值得继续投

站在 CEO / CTO 视角，后续是否继续投入，不应只看愿景，而应重点观察以下问题：

### 13.1 是否解决了组合工具解决不了的问题

如果现有工具组合已经能很好解决问题，平台价值就会被削弱。

### 13.2 是否有明确受益人

必须清楚谁会高频使用、谁会真正受益，而不是“所有人都可能会用”。

### 13.3 是否能量化结果

平台必须在 1 到 2 个迭代内给出清晰指标，例如：

- bug 从提单到 PR 的平均时间
- bug 从提单到回归完成的平均时间
- AI 产出可 review 修复的比例
- QA / 开发往返轮次
- 合并后回归或返工率

### 13.4 平台的维护成本是否可控

如果平台越做越像项目制定制系统，而不是标准化内部能力，那么长期 ROI 会变差。

### 13.5 是否存在清晰的停止线

如果做了一段时间仍然无法在单个闭环中证明显著价值，就应该收缩，而不是继续横向扩张。

---

## 14. 最终判断

对当前平台的阶段性判断如下：

- 平台方向是成立的
- 平台必要性是有条件成立的
- 平台最有价值的部分，不是 AI 本身，而是治理、协作和闭环
- 下一阶段最重要的任务，不是做更多功能，而是打穿更少但更真实的高价值场景

一句话总结：

> 平台不是靠功能堆出来的，而是靠一两条闭环把价值打穿之后，反过来成立的。

当前最合理的推进顺序是：

1. 先证明 `Bug -> AI 修复 -> PR / MR -> QA 回归`
2. 再扩展到 `PRD -> AI 实现 -> 预览验证`
3. 最后逐步补齐质量闭环、组织治理和外部系统联动

---

## 15. 推荐作为团队对齐时反复追问的几个问题

- 我们到底是在做内部研发执行平台，还是内部聊天工具
- 哪个场景能在最短时间内证明平台价值
- 哪些能力必须自研，哪些能力应该借鉴或集成开源项目
- 谁会成为平台的第一批高频用户
- 哪些指标能证明平台真的在缩短研发链路
- 如果 1 到 2 个季度后这些指标没有改善，我们是否愿意收缩方向

如果这些问题始终答得清楚，平台大概率会越做越聚焦。
如果这些问题越来越答不清楚，平台就会越来越像一个重复造轮子的中间层。
